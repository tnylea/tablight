# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What This Project Is

A Chrome extension (Manifest V3, plain JavaScript — no build step, no dependencies) called **Tab Thumbnails & Spotlight**. It gives Chrome two things its native vertical tab strip doesn't:

1. **Side panel tab list** — a vertical list of every tab in the current window, each rendered as a card with a live screenshot thumbnail, favicon, and title. Clicking a card switches to that tab, hovering shows a larger preview, an `×` button closes the tab. The active tab gets a blue outline.
2. **Spotlight tab switcher** — `⌘⇧Space` (Mac) / `Ctrl+Shift+Space` opens a spotlight-style overlay: fuzzy search box on top, a 3×3 grid of thumbnails of the most recently used tabs below. Arrow keys / `Tab` / `Shift+Tab` move the blue selection, `Enter` switches to the selected tab, `Esc` closes. Typing fuzzy-filters all open tabs by title and URL. The grid **includes the current tab, first, with a "Current" pill** as a you-are-here anchor, but the **selection starts on the previous tab**, so shortcut + `Enter` jumps straight back (alt-tab style). So do **`Space` on an empty search box** and **pressing the shortcut again while open** — ⌘⇧Space, Space bounces between two tabs.

The original motivation: Chrome's native vertical tab strip can't be modified by extensions (no API exists for browser-chrome UI), so this extension provides the closest achievable equivalents via the side panel and an injected overlay.

## Architecture

```
manifest.json       MV3 manifest: permissions, command shortcut, content scripts, side panel
keyguard.js         Tiny content script at document_start: registers the window keydown
                    capture listener before any page script so the spotlight always
                    gets keys first (content.js installs/removes the handler)
background.js       Service worker — the hub. Captures thumbnails, stores them,
                    routes all messages, handles the keyboard command
spotlight-core.js   Shared spotlight UI (global TabSpotlight.create). Owns the CSS
                    string, fuzzy matcher, grid rendering, keyboard navigation
content.js          Thin host: mounts spotlight-core inside a closed shadow root
                    on the page when told to by the background
spotlight.html/-page.js  Popup-window fallback for pages content scripts can't
                    touch (chrome://, Web Store). Same core UI, standalone mode
sidepanel.html/css/js    The side panel tab list
```

### Data flow

- **Thumbnail store** (background.js): thumbnails are **keyed by URL (minus fragment), not tab id, and persisted in `chrome.storage.local`** (`unlimitedStorage`): `index` (urlKey → {origin, ts, kind, provisional}) is always in memory, entries `t:<urlKey>` are read on demand, site colours live in one `meta` object. They survive extension reloads and browser restarts; a new tab to a known URL is thumbnailed instantly; a tab on a known origin with no exact match borrows that origin's newest non-provisional thumbnail (`thumbForTab`). Incognito tabs use `privateThumbs` (memory + storage.session) and are never written to disk. Cap 400 entries, og evicted before shots. `thumb-updated` carries `{ tabId, urlKey, origin, data, kind }` and the side panel patches every card on that page, plus same-origin cards that have nothing yet.
- **Thumbnail capture** (background.js): on tab activation (two beats: ~60ms so a thumbnail exists immediately, then a ~650ms "settle" re-capture), page-load complete, window focus, and scroll-stop / visibility signals from the content script, the service worker calls `chrome.tabs.captureVisibleTab` (debounced per window, rate-limited — Chrome caps this API at 2 calls/sec), downscales to a 480px-wide JPEG via `OffscreenCanvas`, and stores it. The **in-memory `thumbCache` Map is the hot path**; `chrome.storage.session` (`thumb_<tabId>`; screenshots capped at 60, 160 total, generated thumbnails evicted before screenshots) is only the durable mirror that survives service-worker restarts and is hydrated once on first use. Every save broadcasts `thumb-updated { tabId, data }` so UIs patch a single card in place.
- **Generated thumbnails for tabs that were never visible** (content.js → background.js): Chrome can only screenshot the visible tab, so the content script, which runs in every http(s) tab whether visible or not, reports `page-meta` at load: the page's `og:image` (or twitter:image / image_src), its `theme-color` or computed body background as `#rrggbb`, and its URL. The background downloads the image (`fetch` with `credentials: 'omit'`, 8s timeout, 6MB cap, must decode to ≥ 120×60, public http(s) hosts only — loopback/private/link-local addresses are refused since the page controls the URL; `page-meta` is only accepted from top-level *active* documents, never prerenders), downscales it through the same pipeline and stores it as a thumbnail with `kind: 'og'`. Colour goes to `metaCache` / `meta_<tabId>` and is broadcast as `meta-updated` so placeholders are tinted with the site colour. **Precedence** (`shouldStore`): a real screenshot (`kind: 'shot'`) always wins; a generated one may replace a screenshot only if the tab has since moved to a different origin. At install the background injects the content script into every open http(s) tab (`injectIntoExistingTabs`) so existing tabs report meta immediately.
- **Page-HTML fallback** (background.js `scanTabHtml` / `sweepMissingThumbs`): for any http(s) tab that has no (or only a provisional) thumbnail for its current origin — discarded tabs have no content script, injection can be blocked — the worker re-requests the tab's URL **without cookies**, reads the first ≤256KB (stops at `</head>`, cancels the body otherwise), regex-extracts og:image / theme-color, and feeds them into the same og pipeline. It skips incognito tabs, URLs that look single-use or identifying (`SENSITIVE_URL` / `SENSITIVE_PATH`: token=, reset, confirm, unsubscribe, login…), and pages that redirect to another origin (a login page's og:image must never become a private tab's thumbnail). Runs on install, startup, worker start, 3s after any tab finishes loading without meta, and on the side panel's **Capture all** button. Scans are deduped per URL for 6h in `htmlScanned`, persisted to `storage.session` so a worker restart doesn't re-request every og-less tab.
- **Idle warm-up** (background.js `runWarmup`, needs the `idle` permission): the only way to get a *real* screenshot of a hidden tab is to show it. After 30s of no input (`chrome.idle`) and only if a normal window is focused, not minimized/fullscreen, **no tab in it is audible and the active tab isn't a call/video site** (`DO_NOT_DISTURB_HOSTS` — idle means "no input", not "not watching"), the worker activates each loaded, non-discarded, overlay-free tab lacking a good screenshot for ~420ms, captures it with `grabVisible(…, { force: true })` (waits out the 2/sec quota instead of deferring; `capture-active` side requests are ignored meanwhile), and re-activates the original tab — or the tab the user clicked, if a click aborted it. The slot is claimed synchronously so idle and **Capture all** can't overlap; `abortWarmup` returns a promise the spotlight command awaits before opening. Our own `mruCache` (touched only by user activations) drives spotlight ordering so warm-up switches don't reorder the grid.
- **Provisional screenshots**: a capture taken while `tab.status !== 'complete'` is stored with `provisional: true`. It never replaces a settled screenshot or an og image of the same origin, and it is replaced by either. Warm-up and HTML scans treat provisional entries as missing.
- **Diagnostics**: `grabVisible` records the last `captureVisibleTab` outcome; `status-updated` / `get-status` carry `{ captureOk, lastError, warming, shots, generated }` and the side panel shows a red notice when screenshots are failing (quota errors are ignored).
- **Spotlight open**: command → background grabs the raw screenshot (not awaited past the `captureVisibleTab` call — encoding happens after the overlay is up), builds a payload (all normal-window tabs sorted by `lastAccessed` desc, `incognito` flag, and thumbnails for only the first 12 non-active tabs) → `tabs.sendMessage` to the content script, which replies `{ open }`. Tabs with an open overlay are tracked in `openOverlays` so a capture never screenshots the overlay itself. Remaining thumbnails are fetched lazily by the core through the `fetchThumbs` callback (`get-thumbs` message) as search results change. If the content script isn't there (page predates install), it's injected via `chrome.scripting.executeScript` and retried; if injection is impossible, the popup-window fallback opens instead (active tab id + incognito flag are stashed first, since the popup steals focus).
- **Theme**: the spotlight is **light by default and dark when the browser is in dark mode or the tab is incognito** (`resolveTheme` in spotlight-core.js; `.ts-light` / `.ts-dark` on the backdrop hold every token). The popup fallback and side panel follow the same rule via `data-theme="dark"` on `<html>`.
- **All tab actions** (activate, close) go through the background via `runtime.sendMessage` — UI contexts never call `chrome.tabs.update` directly.
- Side panel **reconciles** its card list in place on `chrome.tabs` events (30ms debounce; `onUpdated` only when title/favicon/url/status-complete change) and only asks the background for thumbnails it has never seen. `thumb-updated` patches one card; it never triggers a refresh.

## Hard-Won Gotchas (do not regress these)

- **`fetch()` on `data:` URLs is unreliable in MV3 service workers.** Thumbnail decoding uses manual `atob` → `Uint8Array` → `Blob` (`dataUrlToBlob` in background.js). Do not "simplify" it back to `fetch(dataUrl)` — that silently broke all thumbnail generation once already.
- **Grid/flex min-content blowout.** Long unbreakable tab titles will force grid columns unequal and overflow the panel unless the grid uses `repeat(3, minmax(0, 1fr))` and items/meta/titles keep `min-width: 0`. This bug shipped once; the fix lives in spotlight-core.js's CSS string and sidepanel.css.
- **Only the visible tab can be screenshotted.** There is no API to capture background tabs. Tabs never visited since install get a *generated* thumbnail from their `og:image` (see Data flow) and, failing that, a placeholder tinted with the site colour + favicon chip + domain. Placeholders must always render well; not every site has an og:image or a theme colour.
- **Thumbnail values are objects `{ data, kind }`**, where `kind` is `'shot'` or `'og'`. UIs use `kind` to position the image (`object-position: top` for screenshots, `center` for og artwork). `normalizeThumbs` in spotlight-core.js also accepts bare data-URL strings for safety; don't rely on that.
- **The spotlight overlay lives in a *closed* shadow root** with `all: initial` so page CSS can't leak in. Keep all spotlight styles inside the `CSS` string in spotlight-core.js.
- **Keyboard rules in the spotlight**: `←`/`→` move the text caret while the input has text, and only navigate the grid when it's empty. `↑`/`↓`/`Tab` always navigate. `Space` on an empty box = go to previous tab (`goPrevious`; key-repeat ignored; a leading space never matters because the query is trimmed); with text it's a normal character. Choosing the current tab (Enter/click) just closes. `computeResults` never leaves the highlight on the current tab if another result exists. Preserve all of this.
- **`captureVisibleTab` failures are logged with `console.warn`**, never rethrown — but also never swallowed silently (that hid the fetch bug).
- **Never capture while the overlay is mounted.** The shortcut toggles; the second press used to screenshot the overlay into the current tab's thumbnail. `openOverlays` in background.js (marked open *before* the toggle message is sent, mirrored to `storage.session` so it survives service-worker restarts, and re-checked after every in-flight capture) + the `spotlight-closed` message from content.js prevent that. Keep them in sync if you touch open/close.
- **Don't send every thumbnail to the spotlight or re-fetch them all in the side panel.** Both were the cause of "thumbnails take too long": multi-MB payloads plus a full DOM rebuild and image re-decode on every update. The core lazily fetches via `fetchThumbs`; the side panel patches per tab.
- **All spotlight colors must come from theme tokens** on `.ts-light` / `.ts-dark`. A hard-coded color in the CSS string will be wrong in one of the two themes.

## Conventions

- Vanilla JS, IIFE modules, `'use strict'`, no framework, no build step — edit and reload.
- Every `chrome.*` promise that can reject in normal operation (tab closed, no listener, etc.) gets a `.catch(() => {})` or try/catch; the extension must never throw on routine races.
- Favicon URLs are only rendered when they match `/^(https|data):/` (blocks `chrome://favicon` and other unsafe schemes in UI contexts).
- **Spotlight is Raycast-style glass**: a translucent panel (`--ts-panel` ≈ 70% alpha) with `backdrop-filter: blur(44px) saturate(1.8)` over the page, 22px radius, an inset 1px highlight ring in the panel shadow stack, 22px search type, a "Recent"/"Results" section label, *filled* selection (no blue ring) and a bottom action bar (count left, `Switch ↵ · Previous space · Navigate ↑↓` right). The page behind is only lightly dimmed (`--ts-backdrop`), never blurred, so the glass has something to show. The popup fallback paints a soft gradient stand-in. The side panel keeps the flat light/dark token set. Accent `#3b82f6` is used for the caret and match highlights only. Motion: a 70ms opacity fade on open (nothing else on the critical path), disabled under `prefers-reduced-motion`.

## Testing / Verification

No automated tests. Verify changes by:

1. `node --check` every touched JS file (this catches most mistakes; it's been the pre-flight for every change so far).
2. `chrome://extensions` → Developer mode → Load unpacked (or hit ↻ reload on the card after edits).
3. Manual pass: switch between a few tabs (thumbnails should appear essentially instantly, then sharpen ~0.6s later), open the side panel via the toolbar icon, hit `⌘⇧Space` on a normal page (overlay) and on `chrome://extensions` (popup fallback), type to fuzzy-filter (matched characters highlight), navigate with arrows/Tab, `Enter` to switch, `Esc` to close. Check both themes: toggle Chrome's appearance mode and open an incognito window (extension must be allowed in incognito).
   A quick visual check without Chrome: the core can be rendered into a plain page with fake data — see the harness pattern `TabSpotlight.create(div, payload, { theme: 'light' | 'dark', ... })`; `node -e` can also exercise `TabSpotlight.fuzzyMatch` / `bestMatch` / `resolveTheme` with a stubbed `window.matchMedia`.
4. Debug capture issues in the service worker console (`chrome://extensions` → "service worker" link) — capture failures are `console.warn`'d there.

## Known Limitations (accepted, not bugs)

- Real screenshots exist only for pages that have been visible at some point (or warmed up while idle). Other tabs show a thumbnail generated from the site's `og:image`, the site's newest thumbnail, or a colour-tinted placeholder. Thumbnails are persisted in `chrome.storage.local` (on disk, inside the Chrome profile, like Chrome's own tab previews); incognito thumbnails never are. Discarded (memory-saver) tabs have no content script, so they rely on the HTML scan / site fallback.
- The native vertical tab strip itself is untouchable; users who want hover previews there should enable Chrome's built-in **Settings → Appearance → Tab hover preview image**.
- If `⌘⇧Space` doesn't respond, another extension owns the shortcut — reassign at `chrome://extensions/shortcuts`.
- Content scripts run on `http(s)` pages only; `file://` pages get the popup fallback unless the user grants file access.
- **Privileged pages (chrome://, the new tab page, extension pages)** can't be screenshotted unprompted — `captureVisibleTab` fails with "The 'activeTab' permission is not in effect". The shortcut press *is* an invocation, so the command handler captures the current tab even when it isn't http(s), under `activeTab`, before opening the popup fallback; `activeTabGranted` remembers the grant (cleared on navigation) so scheduled captures may use it too. Because thumbnails are keyed by URL, one capture of `chrome://extensions` covers every tab on it. Until captured, UIs render a Chrome-blue icon card via `describeNative` (label "Chrome · Extensions", host line `chrome://extensions`).
- **Keyboard focus in the spotlight**: the core focuses the input on open (several retries) and re-focuses on blur; content.js re-focuses on any `focusin` outside the overlay (throttled). Keys are routed through `window.__tsKeyguard.handler` (installed by keyguard.js at document_start so it beats page listeners): nav keys → `instance.handleKey`, printable → native insert (from overlay) or `instance.typeText` (intercepted), everything else is `stopImmediatePropagation`'d so page shortcuts don't fire. Pages loaded before install get a late-registered fallback listener via `injectIntoExistingTabs` (which injects keyguard.js too).
- **Diagnostics**: `payload.status` lets the spotlight show a red "Screenshots are failing: …" line under the hints; the side panel shows the same notice. `activeTab` is in permissions so the command itself grants capture on the current tab even if site access has been restricted.
- **Open latency is a feature.** Measured warm path: worker steps ≈ 1ms, `tabs.sendMessage` + render ≈ 15ms. What used to make it feel slow: a cold service-worker start (now prevented by a 20s `getPlatformInfo` keepalive), a `captureVisibleTab` awaited *before* sending the payload (removed — the tab is already captured on activation/load/scroll-stop), a 160ms scale/fade animation (now a 70ms fade), and stylesheet parsing per open (now a constructed `CSSStyleSheet` adopted by each shadow root). `prewarm()` loads the MRU tabs' thumbnails into memory on worker start. Don't put anything that touches disk or the compositor back between the keypress and the message.
- **Edits to files do nothing until the extension is reloaded** (↻ on its card at `chrome://extensions`). Chrome never picks up changes to an unpacked extension automatically. If a fix "didn't work", check this first.
